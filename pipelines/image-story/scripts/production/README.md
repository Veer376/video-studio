# Visual Production Pipeline

`scripts/produce_visuals.py` is the scripts-only, crash-safe producer for KathaMind
scene plans that contain primary image prompts, continuation-image prompts, and
optional authored video prompts.

It never writes runtime state into `scenes.json` or `continuity.json`.

## Visual design lock

Production requires an approved project-level visual design in `session.json`:

```json
{
  "visual": {
    "aspect_ratio": "16:9",
    "style_id": "3d_digital_realism",
    "style_prompt": "high-end stylized 3D digital illustration ..."
  }
}
```

The producer treats this as the single source of truth. It prepends the locked
`style_prompt` exactly once to every primary image, continuation image, and authored
video prompt before fingerprinting or provider submission. Scene prompts remain
content-only. A missing design, a conflicting scene-local rendering medium, or an
aspect ratio that disagrees with the session lock fails before paid generation.

Changing the locked style changes the effective asset prompts and therefore their
fingerprints, invalidating style-dependent generated outputs instead of silently
reusing them.

## Canonical subject sheets

Recurring subjects can optionally declare an `image_path` in `continuity.json`:

```json
"viewer_anchor": {
  "role": "Recurring human stand-in for the viewer.",
  "identity_prompt": "stable identity traits only",
  "image_path": "images/subjects/viewer_anchor.png"
}
```

When a scene already lists that subject in its existing `subjects` array, production
automatically attaches the canonical sheet if the file is available. Reference order
is: immediate scene/continuation state first, canonical subject identity sheets next,
then any legacy approved subject anchors and the location anchor. Missing optional
subject-sheet files are skipped; existing files must decode as valid images. Subject
sheet bytes participate in the asset fingerprint, so replacing a sheet correctly
invalidates dependent outputs.

## Runtime files

Inside the selected `library/<project>/` directory:

- `production-manifest.json` — provider/model/fingerprint/reference/job/output state.
- `production-anchors.json` — human-approved recurring subject/location anchors,
  pinned to the exact output SHA-256 and generation fingerprint.
- `.production.lock` — inter-process writer lock.
- `images/scene-001.png` — primary still.
- `images/scene-001-c01.png` — first continuation still.
- `images/scene-001-c02.png` — second continuation still, when present.
- `videos/scene-001.mp4` — optional generated video.

## Zero-cost validation

```bash
python3 scripts/produce_visuals.py plan library/<project>
python3 scripts/produce_visuals.py run library/<project> --images-only --dry-run
python3 scripts/produce_visuals.py status library/<project>
```

## Image production

Start with a small canary rather than the entire project:

```bash
python3 scripts/produce_visuals.py run library/<project> \
  --scene scene-001 --scene scene-002 --scene scene-003 \
  --images-only --image-provider flow --image-model pro
```

Identical reruns are idempotent: an asset is current only when its prompt,
provider/model, ordered reference fingerprints, output bytes, and output path still
match the manifest.

Cross-scene references resolve to the referenced scene's **terminal image** (last
continuation when present, otherwise primary). Within one scene, continuations are
always chained `primary -> c01 -> c02`.

## Continuity approval gates

When `continuity.json` explicitly says a recurring subject or location must be locked
after approval, the producer will stop before an unrelated later appearance until an
approved anchor exists. Direct visual continuations can proceed from their predecessor
without an anchor.

After inspecting and approving an image:

```bash
python3 scripts/produce_visuals.py anchor library/<project> \
  --asset scene-001:primary --subject viewer_anchor

python3 scripts/produce_visuals.py anchor library/<project> \
  --asset scene-001:primary --location discussion_room
```

Anchor approval is bound to the exact generated bytes and fingerprint. If that image
is regenerated, dependent production stops until the anchor is approved again.

## Video prompt map

Videos are never improvised from `asset_strategy`. They require an authored map at
`library/<project>/bin/video-prompts.json` (or an explicit `--video-prompts` path):

```json
{
  "version": 1,
  "scenes": {
    "scene-018": {
      "prompt": "Approved motion prompt for the scene.",
      "provider": "flow",
      "model": "omni_flash",
      "duration": 6,
      "start_asset": "primary",
      "end_asset": "terminal"
    }
  }
}
```

Selectors are `primary`, `terminal`, `c01`, `c02`, or an explicit asset ID.

Then:

```bash
python3 scripts/produce_visuals.py run library/<project> --videos-only
```

The video phase recursively verifies that its image inputs are still current before
spending generation credits.

## Crash/retry semantics

- Flow image and video requests use deterministic, project-scoped
  `Idempotency-Key` values derived from the full asset fingerprint. The same logical
  asset never gets a second creative Flow attempt under a new key.
- Flow video preparation is separated from the paid generation POST. Credit checks,
  uploads, and media-readiness checks happen first; failures there remain `blocked`
  and are rechecked normally on the next run. They never become replayable
  `uncertain` requests.
- A Flow video `job_id` is persisted and reruns poll that same job instead of
  resubmitting it.
- Once the paid submission boundary is entered, the exact Flow request body and
  idempotency key are persisted. Ambiguous failures replay that same request without
  purchasing a second generation.
- Ambiguous non-idempotent Google requests are not automatically repeated.
- `retry` refuses to erase Flow state carrying a durable idempotency key. Replayable
  `submitting`/`uncertain` Flow state is rerun normally with the exact same request;
  a terminal Flow `failed` result is accepted as terminal rather than converted into
  another creative attempt.
- Media is verified before it is marked complete; videos are promoted from
  `.partial.mp4` only after `ffprobe` validation.
- One writer may mutate a project's production state at a time.

## Explicit retry

For a genuinely retryable non-idempotent asset, after verifying that no remote
request is still active:

```bash
python3 scripts/produce_visuals.py retry library/<project> --asset scene-018:video
```

Flow assets in `submitting`, `uncertain`, or `submitted` state with a durable
idempotency key should be rerun directly so the same paid request is safely
replayed/resumed rather than reset. A terminal failed Flow generation is not retried
under a new creative identity. If more than one creative option is desired, generate
explicit candidate variants (for example `v01` and `v02`) and approve one; candidates
are alternatives, not retries.
